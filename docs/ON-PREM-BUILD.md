# Per-customer on-prem сборка (Ф6)

Платформа поставляется в двух режимах из одной кодовой базы:

1. **Центральный мультиарендный хаб** — несколько заказчиков как арендаторы
   (`customers`), скоуп по учётке/подразделению/роли.
2. **Per-customer on-prem** — каждый заказчик получает собственную single-tenant
   сборку на своих серверах. Центральный хаб остаётся источником профилей и
   данных для этих сборок.

Оба режима питаются **профилем заказчика** (данные, не форк кода).

## Профиль заказчика

Структурированное расширение per-tenant namespace. Хранится в таблице
`customer_profiles` (миграция 0035) и/или задаётся файлом профиля для сборки
(`deploy/onprem-profile.example.json`):

| Поле              | Назначение                                            |
|-------------------|-------------------------------------------------------|
| `customer_id`     | арендатор в хабе, чьи данные срезаются                 |
| `domain`          | домен on-прем инстанса (nginx/TLS)                    |
| `single_tenant`   | признак целевой single-tenant сборки                 |
| `enabled_classes` | разрешённые `device_class`                            |
| `feature_flags`   | `ballistics`, `bearing_federation`, `players`, …      |
| `bearing`         | `base_url` + `fed_token` федерации «Пеленга» (Ф3)     |
| `runtime`         | `secure_cookies`, `bind_addr`, `db_path`             |

Профиль — единый вход и для мультиарендного рантайма (по `customer_id`), и для
сборки on-прем бандла.

## Пайплайн

`deploy/build-onprem.ps1` по профилю собирает воспроизводимый бандл. Локально,
без CI (сборка в WSL — Kaspersky блокирует cargo на Windows, как в `deploy.ps1`).

Шаги:

1. **Release-бинари** `outpost-server` + `outpost-export` (в WSL).
2. **Срез данных** заказчика в `seed.db` через `outpost-export` (см. ниже).
3. **Конфиги под домен**: `nginx-<domain>.conf` (с отдельным SSE-location для
   живой карты — `proxy_buffering off`, `proxy_read_timeout 3600s`),
   `outpost-server.service` (systemd), `outpost.env` (APP_SECRET генерируется,
   фиче-флаги из профиля: `BALLISTICS_ENABLED`, `BEARING_BASE_URL/TOKEN`).
4. **README** с инструкцией развёртывания на чистом хосте.

```
.\build-onprem.ps1 -ProfilePath .\onprem-profile.example.json `
    -HubDb /root/outpost-mdm-rs/data/outpost.db -OutDir F:\onprem\example
```

`-ConfigOnly` пропускает WSL-сборку и срез — рендерит только конфиги.

## Срез данных заказчика (`outpost-export`)

`outpost-export <источник.db> <цель.db> <customer_id>` — создаёт свежую БД,
применяет к ней те же миграции (схема + глобальные lookup-сиды: роли, права,
дефолтные настройки) и копирует данные **только** указанного заказчика.

Правила (перечень таблиц берётся из схемы динамически, `src/export.rs`):

- `customers` — очистить сид по умолчанию, вставить строку целевого заказчика;
- таблицы со столбцом `customer_id` — очистить и скопировать `WHERE customer_id = ?`;
- глобальные lookup-таблицы (роли/права/гранты) — оставить как засеяли миграции.

Внешние ключи на время среза выключены; идентификаторы сохраняются (перенумерации
нет). Исходная и целевая БД обязаны быть одной версии схемы (проверяется по числу
применённых миграций). Проверено юнит- и дымовым тестом: чужие арендаторы не
попадают в срез, глобальные роли сохраняются.

Все новые таблицы платформы несут `customer_id NOT NULL … ON DELETE CASCADE`,
поэтому автоматически попадают в срез без правки инструмента.

## Клиентские приложения

Серверный URL приходит клиентам через enrollment-QR (data-driven) — пересборка
APK под домен заказчика не требуется. Точка расширения для брендирования и
baked-in `allowed-classes` под заказчика — **Android product flavors** в
`app/build.gradle.kts` приложений (сейчас flavors отсутствуют — чистое поле для
врезки; заводится по профилю тем же пайплайном при появлении требования к
брендированию).

## Что остаётся при первом реальном on-прем заказчике

- Арендо-осведомлённость глобальных `sessions` и Grafana `auth_request`
  (`src/routes/internal.rs`) — до первого сплита (см. [[reference_project_layout]]).
- Наполнение `customer_profiles` для целевого заказчика (сейчас таблица —
  фундамент; UI/CRUD профиля заводится, когда появится первый on-прем).
