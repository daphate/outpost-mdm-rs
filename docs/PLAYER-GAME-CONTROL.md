# Управление игровыми механиками класса «игроки STALKER» («Ноосфера»)

Операторская сторона игровых механик ПДА «Компас» (`net.afterday.compas`),
встроенная в ситуационный центр MDM. Документ описывает канал доставки команд,
их набор и разграничение доступа. Источник механик — руководство игротехника
ПДА «Компас» (v178, © Afterday Project) и разбор
`pda-compass/out/BUILD-COMPARISON-AND-MECHANICS.md`.

## Что такое «Ноосфера»

В терминах игры «Ноосфера» — это не отдельная сущность на поле, а **режим
централизованного управления всей сетью модулей полигона**. Обычная Зона
статична: игротехник заранее «лепит» её, задавая каждому Wi-Fi-модулю имя вида
`R300` / `A100` (буква — тип угрозы, число — коэффициент силы и радиуса). При
наличии «умной» системы и Wi-Fi-mesh эти параметры можно менять **на ходу**,
алгоритмически и для всех модулей сразу. Такая живая, реагирующая Зона и
называется в руководстве Ноосферой.

Ключевые свойства из руководства:

- конфигурация угроз меняется **после каждого Выброса** и становится
  непредсказуемой для игроков;
- сеть **реагирует на поведение** — например, на число игроков в зоне: если
  сталкеры собираются в группы больше дозволенного правилами, модуль может по
  нарастающей поднять коэффициент с `A100` до `A999` (вся зона — смертельная) и
  «проколоть нарушителей» в их ПДА.

MDM — это и есть та самая «умная система»: он видит всех игроков (позиции и
игровое состояние) и имеет канал команд вниз. Поэтому операторская реализация
Ноосферы естественно ложится на сервер: гейм-мастер отдаёт команды из карты
`/map/players`, а не обходит поле руками.

> Полная Ноосфера в исходном смысле подразумевает и управление параметрами
> самих ESP-модулей (SSID-коэффициенты) через mesh. Это отдельный контур
> (прошивка ESP8266, см. `BUILD-COMPARISON-AND-MECHANICS.md §3.5`); здесь
> реализовано управление игроками через приложение.

## Канал доставки

Игровая команда не требует отдельной инфраструктуры — она ложится в общую
очередь команд устройствам `push_messages` со значением `command = "game.*"` и
доставляется приложению тем же путём, что и прочие push-команды MDM:

```
оператор (карта) ──POST /api/v1/player/{id}/command──▶ push_messages(pending)
        │                                                      │
        │                         устройство ──POST /api/v1/sync──▶ отдаёт pending
        │                                                      │  (long-poll)
        └─ статус в попапе ◀── applied_commands (ack) ◀── приложение исполняет
```

- **Постановка:** `POST /api/v1/player/{id}/command` (одному) и
  `POST /api/v1/players/command` (всем в области — «Ноосфера»).
- **Доставка:** существующий `POST /api/v1/sync` возвращает устройству его
  `pending`-команды и принимает подтверждения (`applied_commands`).
- **Право:** `push.send` (есть у роли operator и выше). Панель управления на
  карте показывается только при этом праве.
- **Изоляция:** команда принимается только для устройства класса
  `stalker_player` в области видимости оператора (customer + unit-scope); иначе
  `404`, без раскрытия чужих устройств.

## Набор команд

| Команда | Механика (руководство) | Полезная нагрузка |
|---|---|---|
| `game.emission` | Выброс (Его Величество); `fake` — тревога без урона | `warn_sec` 0..3600, `duration_sec` 0..3600, `fake` bool |
| `game.threat` | Унифицированная угроза по букве SSID; коэффициент — сила/радиус | `type` R\|A\|M\|C\|B\|Z, `coeff` 1..999 (кроме `Z`), `duration_sec` 0..3600 |
| `game.heal` | Оазис/лечение (H) | `coeff` 1..999, `duration_sec` 0..3600 |
| `game.kill` | «Палач» (QR KILL) | — |
| `game.revive` | «Некромант» (QR REVIVE) | `health_pct` 1..100 |
| `game.faction` | Смена фракции | `faction` STALKER\|MONOLITH\|GAMEMASTER\|DARKEN |
| `game.grant_xp` | Выдать опыт (50 = уровень) | `xp` 1..100000 |
| `game.item` | Выдать предмет (код как в QR) | `code` строка ≤128 |
| `game.violator_mark` | «Прокол нарушителя» (наказание Ноосферы) | `reason` строка ≤200 |
| `game.message` | Текст на ПДА игрока | `text` строка ≤500 |

Буквы угроз: `R` радиация, `A` аномалия, `M` ментал, `C` контролёр, `B` бюрер,
`Z` зов Монолита. Коэффициент трактуется как в игре: `A1` — красной зоны нет,
`A999` — вся зона поражения смертельна. **Исключение — `Z` (Зов Монолита):** по
руководству его сила от коэффициента не зависит, поэтому коэффициент для `Z` не
принимается и в панели управления заблокирован.

Сервер отвергает неизвестные команды и нормализует диапазоны нагрузки, поэтому
из клиента нельзя поставить произвольную или вредоносную команду.

### Свежесть срочных команд

Выброс и угроза (`game.emission`, `game.threat`) действительны «здесь и сейчас».
Живое устройство забирает их за секунды через long-poll `/api/v1/sync`. Защита от
устаревания двухслойная:

- в нагрузку каждой команды сервер вписывает `issued_at` (UTC) — приложение может
  отбраковать команду, доставленную с большим опозданием;
- дренаж `/api/v1/sync` не отдаёт срочные команды старше 120 секунд, чтобы
  устройство, вернувшееся в сеть после долгого офлайна, не проиграло уже
  прошедший Выброс. Команды-состояния (`game.kill`/`game.revive` и прочие)
  доставляются без ограничения по времени.

## Исполнение на устройстве (app-side)

Реализовано в `net.afterday.compas` (сборка vc2010):

- **Приём** — `GameCommandSync` длинным опросом ходит в `POST /api/v1/sync` тем
  же токеном устройства, забирает `pending`-команды и подтверждает исполнение
  через `applied_commands`.
- **Исполнение** — `GameCommandApplier` отображает `game.*` в эффекты движка
  `MasterEffect`, движок применяет их на своём игровом потоке:
  - `game.threat` / `game.heal` — синтетический оверлей влияний на длительность
    (сила по коэффициенту считается штатным `SignalConverter` как для маяка «в
    упор», отдельная калибровка не вводится);
  - `game.emission` — запуск Выброса (урон гейтится числом спутников GNSS, то
    есть настоящее укрытие по-прежнему спасает; `fake` — тревога без урона);
  - `game.kill` / `game.revive` / `game.faction` / `game.grant_xp` / `game.item`
    — прямые операции модели игрока;
  - `game.message` / `game.violator_mark` — текст в журнал HUD.

Ограничения: сообщение, пришедшее при свёрнутом экране, в журнал не попадёт
(журнал — эфемерное состояние экрана). Контур управления самими ESP-модулями
(mesh, смена SSID-коэффициентов на ходу) — отдельная задача уровня прошивки.
