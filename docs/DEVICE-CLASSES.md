# Классы устройств и ситуационные виды карт

Платформа ведёт несколько классов устройств под общим каркасом. Класс задаётся
столбцом `devices.device_class` (миграция 0031); значение по умолчанию —
`android_tactical`. Ниже — расширяемый паттерн: как завести новый класс, не
переписывая ядро.

## Текущие классы

| device_class      | Приём телеметрии                              | Тяжёлое состояние        | Вид карты          |
|-------------------|-----------------------------------------------|--------------------------|--------------------|
| `android_tactical`| `/api/v1/sync` (30-мин) + `/api/v1/position`  | —                        | `/map/tactical`    |
| `acoustic_node`   | федерация с ЦУП «Пеленг» (`fed_bearing`)      | на стороне «Пеленга»     | `/map/antidrone`   |
| `stalker_player`  | `/api/v1/player/state`                         | таблица `player_states`  | `/map/players`     |
| `wearable`        | `/api/v1/position` + метрики OTLP              | приёмник OTLP (без миграции) | `/map/wearables` |

## Общий каркас (переиспользуется всеми классами)

- **Реестр**: `devices` со столбцами `device_class`, `unit_id`, последним
  фиксом (`last_lat/lon/alt/bearing/speed/accuracy`, `last_track_at`).
- **История перемещения**: таблица `device_positions` с прореживанием
  (≥10 м или ≥30 с) — общая функция `routes::position::apply_position`.
- **Живая шина**: `state::LiveBus` (tokio broadcast) → поток
  `GET /api/v1/live/stream` (SSE, скоуп по арендатору). События: `position`,
  `marker`, `player`.
- **Чтение для карт**: `GET /api/v1/geo/*` (GeoJSON), скоуп по `customer_id`.
- **Метрики**: приёмник OTLP (`device_metrics`) принимает произвольные имена —
  виталы/показатели нового класса садятся без миграции.

## Как завести новый класс

1. **Значение класса.** Выбрать строку `device_class` (например `sensor_relay`).
   Устройство заводится администратором и проходит enroll как обычно —
   транспорт платформо-независим, Android-поля опциональны.

2. **Приём телеметрии.** Выбрать по природе устройства:
   - движущееся с координатами → слать на общий `POST /api/v1/position`
     (позиция + история + событие `position` уже готовы);
   - со специфическим состоянием → добавить лёгкий канал по образцу
     `routes::player` (вызвать `apply_position`, затем upsert своего состояния
     и публикация события в шину);
   - метрики/виталы → слать по OTLP (`/v1/metrics`), приёмник примет любые
     имена без миграции;
   - внешняя система как источник истины → адаптер федерации по образцу
     `routes::fed_bearing` (не дублировать чужой расчёт).

3. **Тяжёлое состояние (если нужно).** Отдельная таблица per-class с
   `customer_id NOT NULL … ON DELETE CASCADE` и ключом `device_id` (образец —
   `player_states`, миграция 0034). Лёгкое/произвольное — через OTLP, без
   таблицы.

4. **Чтение для карты.** Добавить `GET /api/v1/geo/<класс>` в `routes::geo`:
   выборка устройств `WHERE customer_id = ? AND device_class = '<класс>'` с
   позицией, при необходимости LEFT JOIN своего состояния или последних
   метрик OTLP; вернуть GeoJSON FeatureCollection.

5. **Вид карты.** Шаблон `templates/map_<класс>.html` по образцу
   `map_players.html`/`map_wearables.html` (общий каркас MapLibre + OSM-подложка
   + слой точек, опрос своего `/geo`-эндпоинта и/или живой поток). Маршрут
   `/map/<класс>` в `routes::web` + ссылка в `_nav.html`.

Пункты 1–3 при чисто позиционно-метрическом классе (как `wearable`) сводятся к
выбору значения `device_class`: приём уже покрыт `/api/v1/position` и OTLP,
миграций не требуется — остаются только пункты 4 и 5.

## Скоуп и разграничение

Все новые таблицы обязаны нести `customer_id NOT NULL … ON DELETE CASCADE`
(готовность к per-customer выгрузке и on-прем сборке, см. Ф6). Разграничение по
подразделению (`unit_id`) вплетается в выборки по мере надобности.
